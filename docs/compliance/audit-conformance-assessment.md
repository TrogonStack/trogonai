# Audit Conformance Assessment: trogon-telemetry / trogon-semconv / a2a-gateway audit_ingress

> Internal self-assessment, not a certification. This document records TrogonAi engineering's own reading of its code against a borrowed vocabulary; it is not an attestation by any external auditor or standards body.

The three-tier vocabulary below (Level 1 structured logging, Level 2 event sink SPI plus OTel correlation, Level 3 tamper evidence plus Decision BOM) is defined in specification `AUDIT-COMPLIANCE-1.0`, section 3 and sections 4-11.

## Scope

- `rsworkspace/crates/trogon-telemetry` (logging, tracing, metrics setup)
- `rsworkspace/crates/trogon-semconv` (generated OTel semantic conventions)
- `rsworkspace/crates/a2a-gateway/src/audit_ingress.rs` (ingress audit envelope construction)
- `rsworkspace/crates/a2a-nats/src/audit/` (envelope wire shape and NATS emitter actually invoked by the gateway's dispatch path, read because `audit_ingress.rs` alone is not wired to a publish call)

## Level 1: Structured logging

AUDIT-COMPLIANCE-1.0 section 4-5 requires a canonical audit entry schema (timestamp, event_type, agent_id, action, decision, reason, latency_ms, metadata) and a backend SPI where `write()` never raises, is thread-safe, and supports multi-backend fan-out.

| Requirement | Status | Evidence |
|---|---|---|
| Structured, machine-parseable log output | Met | `trogon-telemetry/src/lib.rs` `init_logger` builds `tracing_subscriber::fmt::layer().json()` for both the stderr layer and the optional file layer (lines 96-109). Every log line is a JSON object, not free text. |
| Timestamped, leveled entries | Met | Standard `tracing` macros (`tracing::info!`, `tracing::warn!`) used throughout `trogon-telemetry/src/lib.rs` (lines 143, 158-161) carry level and timestamp via the `tracing_subscriber::fmt` formatter. |
| Canonical audit-entry schema (agent_id, action, decision, reason, latency_ms, metadata) | Not met | No `AuditEntry`-shaped struct exists in `trogon-telemetry`. `a2a-nats/src/audit/envelope.rs` `AuditEnvelope` (lines 102-114) is the closest analogue for the a2a-gateway path specifically (`agent_id`, `method`, `req_id`, `started_at`, `latency_ms`, `outcome`, `params_fingerprint`, plus `AuditEnvelopeFields` extras) but this is a single ingress-audit-specific type scoped to `a2a-nats`/`a2a-gateway`, not a crate-wide canonical schema that other services reuse. |
| Non-blocking write path | Met | `a2a-gateway/src/runtime/audit_publish.rs` `spawn_gateway_audit_publish` spawns a detached `tokio::spawn` task per request (lines 24-40) so a publish failure cannot block the ingress reply; the docstring states this explicitly: "Callers MUST NOT depend on the envelope being durably stored before they reply." |
| `write()`/`emit()` never raises to caller | Met | `a2a-nats/src/audit/emitter.rs` `NatsAuditEmitter::publish` (lines 44-71) catches the NATS publish error and only logs `tracing::warn!`; it never propagates a `Result` to the dispatch caller. |
| Multi-backend fan-out | Not met | There is exactly one sink (`NatsAuditEmitter`, plus a `NoopAuditEmitter` for disabled deployments in `a2a-nats/src/audit/emitter.rs` lines 94-114). No mechanism registers more than one backend or dispatches one entry to several destinations simultaneously. |
| File permission / rotation hardening (0600, parent dir creation) for any local audit log | Partially met | `trogon-telemetry/src/log.rs` `ensure_log_dir` (lines 39-53) creates parent directories automatically and resolves a platform-specific log directory, but this is the general application log file, not an audit-specific file, and the code does not set an explicit `0o600` permission mode. |

**Level 1 verdict: Partially met.** The logging substrate (JSON structured output, non-blocking, no-throw sinks) is solid, but there is no canonical, crate-wide `AuditEntry` type or multi-backend fan-out; the one audit-shaped schema that exists (`AuditEnvelope`) is local to the a2a-gateway ingress path, not a shared `trogon-telemetry` concept.

## Level 2: Event sink SPI + OTel correlation + cross-component correlation

AUDIT-COMPLIANCE-1.0 sections 6-8 require a versioned governance-event envelope, a `GovernanceEventSink` protocol (`emit`/`shutdown`/`force_flush`, batch export, circuit breaker, DROP_OLDEST backpressure), and OTel trace/span correlation fields actually populated from real trace context.

| Requirement | Status | Evidence |
|---|---|---|
| OTel tracer/meter/logger provider setup | Met | `trogon-telemetry/src/trace.rs`, `src/metric.rs`, `src/log.rs` each build an `Sdk*Provider` over OTLP HTTP exporters and are wired together in `lib.rs` `try_init_otel` (lines 169-193): `TracerProvider`, `SdkMeterProvider`, `SdkLoggerProvider` all constructed from one shared `Resource`. |
| Tracing/logs bridge so log records carry trace context automatically | Met | `trogon-telemetry/src/lib.rs` line 127 wires `OpenTelemetryTracingBridge::new(&logger_provider)` into the `tracing_subscriber::registry()` alongside `tracing_opentelemetry::layer()` (line 117), so any log emitted inside an active `tracing::Span` is automatically correlated to that span's trace/span ID by the OTel log bridge. |
| Generated, CI-enforced semantic conventions for span/attribute/metric names | Met | `trogon-semconv/src/lib.rs` documents that `gen/` is generated from a Weaver registry (`otel/semconv/`) and re-exports `attribute`, `metric`, `span` modules; `trogon-semconv/src/gen/span.rs`, `gen/metric.rs`, `gen/attribute.rs` contain the generated constants. Five dylints (`telemetry_attribute_literal`, `telemetry_key_value_literal`, `telemetry_metric_construction`, `telemetry_metric_name_literal`, `telemetry_span_name_literal`, registered in `rsworkspace/dylints/trogon_lints/src/lib.rs` lines 16-21, 498-517) force call sites to use these generated constants instead of string literals. |
| Governance-event envelope with `schema_version`, `event_id`, `kind` enum, `trace_id`/`span_id` fields | Partially met | `a2a-gateway/src/audit_ingress.rs` `A2aIngressAudit` (lines 168-178) has `request_id`, `tenant`, `agent`, `skill`, `outcome` (an `IngressAuditOutcome` enum: `Allow`/`Deny`), `reason`, `shadow`, `traceparent`. There is no `schema_version` field and no `kind` taxonomy analogous to AUDIT-COMPLIANCE-1.0's 12-value `GovernanceEventKind` enum (`POLICY_CHECK`, `TOOL_CALL_BLOCKED`, etc.); the outcome enum only distinguishes allow/deny, not the richer event classification the spec's Level-2 tier expects. |
| `trace_id` populated from real OTel span context (not an ad-hoc ID) | Not met | `a2a-gateway/src/runtime/dispatch.rs` line 221: `let trace_id = Uuid::new_v4().to_string();`. This UUID is threaded through `tier1_denial.rs` (line 83) and into `AuditEnvelopeFields.trace_id` (`a2a-nats/src/audit/envelope.rs` line 83) at every audit-emit call site in `dispatch.rs` (lines 309, 373, 478, 523, 595, 638, 686). It is a per-request correlation UUID generated independently of the `tracing`/`opentelemetry` span context that `trogon-telemetry` establishes; it is never read from `tracing::Span::current()` or an OTel `SpanContext`. A human can correlate audit envelopes to each other via this UUID, but not to the OTel trace that the OTLP exporter ships for the same request, because they are different identifier spaces. |
| Event sink SPI (`emit`/`shutdown`/`force_flush` protocol, pluggable backends) | Not met | `a2a-nats/src/audit/emitter.rs` defines an `AuditEmitter` trait (lines 13-28) with `publish` and `publish_task_lifecycle`, implemented by `NatsAuditEmitter` and `NoopAuditEmitter`. There is no `shutdown(timeout_ms)` or `force_flush(timeout_ms)` method, no `SinkExportResult` (`SUCCESS`/`FAILURE`/`DROPPED`) return type, and nothing resembling a `GovernanceEventSinkBase` default-implementation convenience type. |
| Batching / background worker / circuit breaker for event export | Not met | `spawn_gateway_audit_publish` (`a2a-gateway/src/runtime/audit_publish.rs` lines 24-40) spawns one `tokio::spawn` task per audit envelope; there is no shared background worker thread, no queue, no batch export cycle, and no circuit-breaker state machine (open/half-open/closed) anywhere in `a2a-gateway` or `a2a-nats`. |
| Bounded queue with DROP_OLDEST backpressure and dropped-event metrics | Not met | No queue exists at all in the audit publish path (each envelope gets its own spawned task), so there is nothing to apply backpressure to and no dropped-event counter. |
| Cross-component correlation via a shared identifier | Partially met | Within a single gateway request, the `Uuid::new_v4()` `trace_id` and `req_id` correlate all audit envelopes for that request (`dispatch.rs`). There is no evidence of this identifier, or any other, being propagated to or reconciled with other components (scheduler, ARD) to give an end-to-end cross-service correlation key. |

**Level 2 verdict: Not met.** The OTel provider setup and generated-and-CI-enforced semantic conventions are strong and exceed what the spec's Level 2 asks for on the pure-observability side. But the audit-specific half of Level 2, an event sink SPI with lifecycle methods and backpressure/circuit-breaker semantics, and OTel-derived (rather than ad-hoc UUID) trace correlation on audit envelopes, does not exist. The `trace_id` field name in `AuditEnvelopeFields` is misleading in this context: it looks like OTel correlation but is populated from `Uuid::new_v4()`, not from the tracing span context that `trogon-telemetry` establishes.

## Level 3: Tamper evidence + Decision BOM

AUDIT-COMPLIANCE-1.0 sections 9-11 require a Merkle/hash-chained audit log (`previous_hash`/`entry_hash` per entry, `verify_chain()`, Merkle proof generation/verification) and a Decision BOM reconstructor that queries audit, trust, policy, and trace sources to rebuild the full context of a governance decision.

| Requirement | Status | Evidence |
|---|---|---|
| Per-entry content hash | Partially met | `a2a-nats/src/audit/envelope.rs` `AuditEnvelope::new` (lines 116-146) computes `params_fingerprint` as a SHA-256 digest of the raw request payload bytes (lines 128-134, via `sha2::Sha256::digest`). This is a hash of that single entry's parameters, not a hash that commits to the entry's other fields or to any preceding entry. |
| Hash-chain linkage (`previous_hash` / `entry_hash` per entry) | Not met | No field or computation anywhere in `a2a-gateway`, `a2a-nats`, `trogon-telemetry`, or `trogon-semconv` links one audit envelope's hash to the previous envelope's hash. `grep` for `previous_hash`, `entry_hash`, `hash_chain`, `chain_root`, `verify_chain`, and `merkle` across `rsworkspace/crates` returns zero matches in these areas (the only unrelated SHA-256 usage found workspace-wide is `content_digest_sha256` in `a2a-gateway/tests/aauth_roundtrip.rs`, which is RFC 9421 proof-of-possession signing, not audit chaining). |
| Merkle tree construction and inclusion-proof generation/verification | Not met | No Merkle tree data structure, `get_proof()`, or proof-verification routine exists anywhere in the surveyed crates. |
| `verify_chain()` integrity check | Not met | No such function exists. There is no code path that recomputes and compares hashes across a sequence of stored audit entries. |
| Decision BOM reconstruction (audit + trust + policy + trace sources, completeness score) | Not met | No `DecisionBOM`, `BOMField`, or reconstructor type exists. There is no code that, given a decision or trace id, queries multiple data sources (audit history, trust scores, policy evaluations, OTel spans) and assembles a single reconstructed record. |
| Compliance framework engine (SOC 2 / HIPAA / EU AI Act / GDPR controls, violations, scoring) | Not met | No compliance-control, compliance-mapping, or compliance-report types exist in the surveyed crates. (Out of scope for WI-18 strictly, but confirmed absent for completeness since Level 3 in the source spec bundles it with the audit chain.) |
| Durable, tamper-resistant storage substrate | Partially met (structural, not cryptographic) | Audit envelopes are published over NATS (`NatsAuditEmitter::publish`, `a2a-nats/src/audit/emitter.rs` lines 44-71) as fire-and-forget publishes; whether they land on a replicated JetStream stream is a deployment/subject-mapping concern outside the crates reviewed here, and even if they do, JetStream's ordered, durable, replicated log is provenance-by-construction (the storage layer resists tampering), not provenance-by-cryptographic-proof (a third party independently verifying integrity without trusting the storage layer). No incremental hash chain is computed at write time regardless of the underlying stream's durability. |

**Level 3 verdict: Not met.** Beyond a single-entry parameter fingerprint, there is no cryptographic chaining, no Merkle proof machinery, no chain-verification routine, and no Decision BOM concept anywhere in the reviewed code.

## Overall conformance

**TrogonAi currently sits between Level 1 and Level 2, closer to Level 1, and does not reach Level 2 in full.**

- Level 1 (structured logging): Partially met. JSON structured logs and non-blocking, no-throw publish paths exist; a canonical, crate-wide audit-entry schema and multi-backend fan-out do not.
- Level 2 (event sink SPI + OTel correlation): Not met as a whole, though the underlying OTel provider setup and CI-enforced semantic-convention discipline in `trogon-telemetry`/`trogon-semconv` are ahead of what the spec's Level 2 asks for on the general-observability side. The audit-specific requirements (sink SPI with lifecycle/backpressure/circuit-breaker semantics, and genuine OTel-derived trace correlation on audit envelopes rather than an independently generated UUID) are missing.
- Level 3 (tamper evidence + Decision BOM): Not met. No hash chaining beyond a single-entry parameter fingerprint, no Merkle proofs, no Decision BOM.

## Gap list (feeds WI-20)

WI-20 ("Tamper-evident audit chain over JetStream") is not yet built. The gaps below are what it needs to close, in order of what the chain design most directly depends on:

1. **No hash-chain linkage between audit entries.** `AuditEnvelope` computes a per-entry `params_fingerprint` (SHA-256 of the payload only) but nothing links one entry's hash to the previous entry's hash. WI-20's design (incremental SHA-256 over each event plus the previous hash, stored as a NATS message header or companion KV entry keyed by stream sequence) has no precursor to build on; it starts from zero in this codebase.
2. **No `verify_chain()`-equivalent.** There is no stream-replay verification routine anywhere in `a2a-gateway`, `a2a-nats`, or `trogon-telemetry`. WI-20 needs to introduce this from scratch, including deciding what "stream sequence remains authoritative" (the ADR 0013 invariant referenced in the prior AGT-vs-TrogonAi analysis) means for chain verification order.
3. **`trace_id` on the audit envelope is not an OTel trace ID.** It is `Uuid::new_v4()` (`a2a-gateway/src/runtime/dispatch.rs` line 221), generated independently of the `tracing`/OpenTelemetry span context `trogon-telemetry` establishes. Before or alongside WI-20, this should be replaced with the real OTel trace id (e.g., via `tracing::Span::current()` extraction) so audit envelopes correlate with OTLP-exported traces, not just with each other.
4. **No event sink SPI to hang tamper evidence off of.** `AuditEmitter` (`a2a-nats/src/audit/emitter.rs`) has only `publish`/`publish_task_lifecycle`; there is no `shutdown`/`force_flush`/`SinkExportResult` shape. WI-20's chain-verification and export logic will need a home; whether that home is a new sink type or an extension of `AuditEmitter` is an open design question WI-20 should settle explicitly.
5. **No canonical, crate-wide audit-entry schema.** `AuditEnvelope` is scoped to a2a-gateway ingress; a tamper-evident chain that is meant to cover more than one component's audit trail needs a shared schema (or at least a shared hashing contract) before WI-20 can be applied uniformly.
6. **No Decision BOM concept to reconstruct once a chain exists.** Even after WI-20 lands a verifiable chain, there is nothing that reconstructs a decision's full context (policy evaluation, trust state, trace spans) from that chain. This is a distinct follow-on gap, not part of WI-20's stated scope, but worth tracking as a Level-3 completion item once WI-20 ships.
7. **No multi-backend fan-out or circuit breaker for audit export.** Fire-and-forget, one-`tokio::spawn`-per-entry publishing (`spawn_gateway_audit_publish`) has no queue, no batching, and no failure-isolation semantics. A durable hash chain built on top of an unreliable, un-backpressured publish path risks silent gaps in the chain; WI-20 should specify what happens to chain continuity when a publish is dropped.
