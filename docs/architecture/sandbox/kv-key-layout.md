# KV key layout for tenant-scoped records

The broker keeps snapshot tags, named-lease index entries, drives and prewarm policies in NATS KV buckets, one key per tenant and name. It keeps tenant limits and the image and host_mount allow-lists one key per tenant, and pushes each tenant's checkpoints to a per-tenant OCI repository. This page explains why those keys and paths have their current shape, what a broker does with records written under the previous shape, and what an operator should check before and after a rollout.

## Why the old keys were unsafe

The old key was `{tenant}_{name}`, with `:`, `/` and `.` folded to `_`. That mapping loses information in two ways:

- `_` separates the tenant from the name, but tenant ids could contain `_` too. Tenant `acme` with tag `team_prod` and tenant `acme_team` with tag `prod` both used the key `acme_team_prod`.
- Folding made names that differ only in `.`, `:`, `/` or `_` the same key: tag `v1.2` and tag `v1_2` shared one record.

Two different owners sharing a key means one can overwrite, read or block the other. Listing a tenant's tags matched keys by prefix only, so tenant `acme` also saw every tag of tenant `acme_team`.

Records keyed by the tenant alone had the same problem: tenants `a.b`, `a:b` and `a_b` all used the key `a_b`, so they shared one set of limits and one image and host_mount allow-list. The snapshot repository `snapshots/{tenant}`, with `:` and `/` folded to `_`, sent tenants `a:b`, `a/b` and `a_b` to the same repository.

## The current layout

Keys come from `tenant_scoped_kv_key` in `rsworkspace/crates/sandbox/trogon-sandbox-protocol/src/kv_key.rs`:

- the tenant keeps `[A-Za-z0-9-]` and writes every other byte as `=HH` (uppercase hex),
- then a single `_`,
- then the name, which keeps `[A-Za-z0-9_-]` and escapes every other byte the same way.

The tenant part never contains `_`, so the first `_` always ends it, and both escapes decode to exactly one value. Two different `(tenant, name)` pairs therefore never share a key, and a key that starts with a tenant's prefix belongs to that tenant. Keys only use `[A-Za-z0-9_=-]`, which NATS KV accepts.

For the usual ids (tenant in `[A-Za-z0-9-]`, name in `[A-Za-z0-9_-]`) the current key is byte-for-byte the old key, so most stored records do not move.

Snapshot tag values also carry an `owner` field naming the tag they belong to.

Records keyed by the tenant alone use `tenant_kv_key`, which is the tenant part above on its own: `a.b` becomes `a=2Eb` and `a_b` becomes `a=5Fb`. Prewarm keys are `tenant_scoped_kv_key(tenant, digest)` with the digest written as `sha256_<hex>`. The previous shapes remain available as `legacy_tenant_kv_key` and `legacy_tenant_scoped_kv_key` for the fallback reads described below.

Snapshot repositories come from `snapshot_repository_for_tenant` in `trogon-sandbox-protocol`. A tenant id without `:` or `/` keeps `snapshots/{tenant}`. Any other tenant, and the tenant named `tenant-hex`, moves to `snapshots/tenant-hex/{hex of the tenant id}`, so `a:b` uses `snapshots/tenant-hex/613a62`. A kept path has one segment after `snapshots/` and a moved path has two, so no two tenants share a repository. The hex form uses only lowercase letters and digits because OCI repository names allow nothing else.

## What happens to records under an old key

A record needs attention only when its old key differs from its current key: the tenant id contains anything outside `[A-Za-z0-9-]`, or the name contains `.`, `:`, `/` or other escaped bytes. For those records:

- **Drives.** Reads, attach, release and delete look at the current key, then at the old key. A drive record names its own id, so the broker only uses a record whose id matches the request. Records stay under the old key until they are deleted. Creating a drive that already exists under its old key fails with "already exists".
- **Named leases.** Lookups fall back to the old key. Releases clear the old key only when it still points at the releasing lease. New claims always use the current key. The broker already checks that a resolved lease belongs to the requesting tenant, so a shared old key never hands over another tenant's lease. Old entries go away as their leases end.
- **Snapshot tags.** Reads fall back to the old key. The next set of the tag moves it: the broker writes the stamped record under the current key and then deletes the old key at the revision it read. Clearing a tag also removes an old-key copy left by an interrupted move. Listing returns stamped records whose owner is the tenant, plus unstamped records under the tenant's old prefix.
- **Prewarm policies.** A prewarm record names its own tenant and digest, so reads fall back to the old key only for a record that names the reading tenant. The next write of the policy moves it to the current key and deletes the old one. Deleting a policy removes both.
- **Tenant limits and allow-lists.** Reads use the current key, and fall back to the old key while the tenant has no record under its current key. `trogon-sandbox-admin` writes only the current key, shows the same record the broker reads, and its `clear` commands delete both keys so a cleared policy cannot come back from the old one.
- **Snapshot repositories.** Only tenants whose id contains `:` or `/`, and the tenant named `tenant-hex`, change repository. New checkpoints go to the current repository. Tag and prewarm restores, retention eviction, `snapshot_delete` and `trogon-sandbox-admin snapshot delete` ask the registry for the manifest in the current repository, then in the old one, and use whichever has it. Nothing is copied between repositories.
- **Monthly quota records.** They move from `{tenant}_{yyyy}-{mm}`, with `:` folded to `_`, to the tenant-scoped key with `{yyyy}-{mm}` as the name. Tenants whose id has no `_`, `.`, `:` or `/` keep their key. A counter cannot fall back on every read the way a limit does, because writes to the current key would be lost behind a stale old record. Instead, the first time the broker touches a tenant's month and finds no current record, it copies the old record into the current key with a create, so two brokers racing to seed it write it once. From then on every reservation, release, attempt and snapshot count goes through compare-and-swap on the current key only. The old record is never written or deleted, so usage is never counted twice. `trogon-sandbox-admin quota show` reads the current key and falls back to the old one for a month the broker has not touched yet.
- **Lease usage.** Entries used to sit under the bare lease id, so a tenant total had to fetch every entry in the bucket. New entries use `tenant.<tenant>.<lease>`, three subject tokens built from `tenant_scoped_kv_key`, in the `sandbox-lease-usage` bucket. A tenant total asks the server for two filters, `tenant.<tenant>.>` and `*`, so it neither lists nor reads another tenant's scoped entries. The `*` filter matches the bare legacy keys of every tenant, one token each, so those are read and kept only when their `tenant` field matches. A read of one lease looks at the scoped key, then at the legacy key, and only returns an entry whose `tenant` field matches. The first write of a lease whose entry is still under the legacy key copies it to the scoped key with a create, then deletes the legacy key at the revision it read. An entry present under both keys counts once, as the scoped entry, so counts an older broker adds after the move are not seen. That undercounts but never double counts. The bucket keeps its seven day `max_age`, so legacy entries age out on their own.

## Release refunds and drive claims

Releasing a lease removes its active record first and then refunds quota and clears its drive claims. A release that stops partway is safe to redo.

- **Refund applied once, by receipt.** The refund and a receipt for the lease are written in one compare-and-swap of the monthly quota record, so a redo that finds the receipt does nothing. A broker that stops before the write loses nothing, because the redo applies it. One that stops after it cannot double refund. A delete-by-id writes a pending-purge marker with the refund amounts and a timestamp. The release and the reconciler's redo both refund into the month of that timestamp, so every attempt lands on the same record and sees the same receipt. Receipts are kept for 8 days, longer than the 7-day marker max age, and pruned on the next refund.
- **Receipt growth.** A record keeps at most 4096 receipts and at most 384 KiB of them (lease id plus 24 bytes each), whichever binds first, leaving the record well under the 1 MiB payload limit even with long lease ids. Past the cap the oldest go first, so only a redo of a release older than the newest receipts could refund twice.
- **No stream for `lease_released`.** The broker creates no JetStream stream for `lease_released`, and every consumer uses a core subscription, which a stream's dedupe does not affect. The `Nats-Msg-Id` is a hint for a future stream consumer, not what prevents a double refund. Treat `lease_released` as at-least-once, keyed by lease id.
- **Drive claims carried by the marker.** The marker records the lease's drives when the delete starts, and a retried delete or the reconciler releases exactly those claims, trying all of them and keeping the marker when any fails. Clearing a claim is exact-owner, so repeating it is harmless.
- **Orphaned claims are swept.** A claim can outlive its lease when a broker stops before the release runs. A grant sets its drive claims before it writes the active lease record, so a claim with no record may belong to a grant in flight. On each reconciler tick the broker lists up to 1024 claims and releases at most 32 whose lease has no active record, release marker, purge marker or pending redrive and whose claim is older than `SANDBOX_ORPHAN_DRIVE_CLAIM_GRACE_SECS` (default 1800, raised to twice `SANDBOX_PROVIDER_DISPATCH_TIMEOUT_SECS` when that is larger). Age is the revision time the drive bucket reports for the claim. A store that reports none ages the claim from the broker's first sighting, so a restart restarts the clock. The release is guarded by the revision the claim was read at, so a claim re-written meanwhile is left alone. Nothing is persisted for the sweep.
- **Every other release is durable too.** A release that is not a purge, and a purge with no pending-purge marker (delete by name, a duplicate idempotent grant), writes a release marker in the `sandbox-lease-pending-release` bucket before it removes the active record. The marker holds the refund amounts, the month timestamp, the drive claims, the lease's name and the `lease_released` event. The release refunds through the same receipt mechanism, announces, and drops the marker. The reconciler redoes a marker older than a minute whose active record is gone, from the marker alone, and drops the marker of a release that stopped before removing the record (the lease is still live and nothing is owed). Markers are created, not overwritten, so concurrent releases of one lease share one timestamp and one receipt. The marker's `max_age` is 3 days, under the 8-day receipt retention. A release that loses the race for the record clears a marker it created itself and leaves the winner's alone.
- **Operator clear for a capped freeze marker.** After the settle attempts are exhausted a freeze marker stays until someone resolves it. Run `trogon-sandbox-admin lease clear-freeze <lease-id>` to drop the marker and accept the worker state as it is, or `trogon-sandbox-admin lease retry-freeze <lease-id>` to reset the attempts so the reconciler asks the worker again. Both refuse a marker still within its attempts unless `--force` is given, and they move the dispatch journal before the active record so the two stay equal. They use direct KV access with the operator's NATS credentials, like the other admin verbs (`--active-lease-bucket`, `--idempotency-bucket`).

Residual risk: a release that creates its marker after another release of the same lease finished, and then stops before clearing it, leaves a marker whose timestamp can fall in a later month than the first. A redo would then refund into that month's record and, across a month boundary only, refund twice. The `lease_released` event is at-least-once: a stop after announcing and before the marker is dropped announces again. The release's other steps (the usage final stamp, the metrics gauge, command-state purge) are not redone. Nothing sweeps drive attachments that no marker or lease explains, because such a sweep would race a grant that sets the claim before the active record.

Mixed versions: a broker that predates receipts claims the marker's refund before applying it and does not write receipts, and rewriting a quota record drops receipts it does not know. Keep deletes by id paused while brokers differ, so no purge refunds under both schemes. Roll brokers over without leaving leases mid-release.

## Limits of the fallback

An unstamped snapshot tag or named-lease entry written before the current layout does not say who wrote it. If two owners already folded to the same old key, the stored value is whichever wrote last, and the broker cannot tell which owner it belongs to. It treats it as belonging to the tenant that reads it. Drives cannot be misread this way, but an old-key drive record still occupies its key: creating a different drive whose current key equals that old key fails with "already exists" until the old drive is deleted. This only happens in deployments that had tenant ids with `_`, `.`, `:` or `/`, or tags that differ only in those characters.

Limits and allow-lists have no owner field either. Until a tenant gets a record under its current key, it reads the shared old key. A tenant `a.b` therefore still uses a record that the admin tool wrote for `a_b` under the old layout, and the other way round, until one of them is written again. Clearing either tenant deletes the shared old record for both.

Snapshot restores probe the registry for the moved tenants only. A probe that fails for any reason, such as a registry outage, counts as "not there", so the broker falls back to the current repository and the restore fails as it would for a missing snapshot. The tenant named `tenant-hex` moves as well, so no tenant writes to `snapshots/tenant-hex`, the prefix of the moved repositories. Its legacy repository is still read for old snapshots, so a registry that grants access by repository prefix should not grant `snapshots/tenant-hex` to that tenant once its old snapshots are gone.

Quota counters of tenants that shared an old key, such as `a:b` and `a_b`, are both seeded from the shared usage. Each starts the month with the other's usage counted against it, which can deny early but never lets a tenant exceed its budget. Seeding happens once per tenant and month, so the overcount ends at the next month.

## Rollout

1. Check the tenant ids in use. If every tenant id matches `[A-Za-z0-9-]+`, only names with `.`, `:` or `/` change keys, and no tenant could have collided with another.
2. Upgrade brokers and gateways. Until every broker is upgraded, an older broker still reads and writes old keys, so a tag moved to its current key by a new broker is invisible to an old one. Keep the mixed-version window short, or pause tag writes during it. Quota counters are affected the same way: once a new broker seeds a tenant's current quota key, an old broker keeps counting that tenant's usage in the old key, which the new brokers no longer read.
3. If any tenant id had `_`, `.`, `:` or `/`, list each affected tenant's tags after the upgrade and set each one again, so every tag carries an owner stamp under its current key.
4. For the same tenants, run the admin tool's `set` for each limit, and `set` with `--replace` for each image policy and host_mount policy the tenant should have. That writes the current key and ends the shared fallback. Where two tenants folded to one old key, set both before clearing either.
5. Old snapshots of tenants with `:` or `/` stay in the old repository and keep restoring from it. Nothing has to move. To retire the old repository, take new checkpoints, point the tags at them, and let retention evict the old digests.
