# Goose (aaif-goose/goose, formerly block/goose)

Produced by the ACP product case-study pass (2026-07-30), then adversarially verified; corrections below override the body where they conflict.

## Goose: research case study for trogonai ACP integration

Goose (github.com/aaif-goose/goose, historically github.com/block/goose) is Block's open source, local-first coding agent, donated to the Linux Foundation's new Agentic AI Foundation (AAIF) in early 2026 alongside MCP and AGENTS.md (https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation, https://goose-docs.ai/blog/2026/04/07/goose-moves-to-aaif/). The GitHub org is now `aaif-goose`, not a fork of `block/goose` but the canonical repo under new governance (verified via `gh api repos/aaif-goose/goose`: `fork: false`). It is Apache-2.0 licensed, Rust-based, at v1.45.0 as of 2026-07-29 (https://github.com/aaif-goose/goose/releases).

### ACP status: native, both agent and client

Goose implements ACP natively as an **agent**: the CLI subcommand `goose acp` runs a stdio JSON-RPC ACP server, listed directly on Zed's agent registry (https://zed.dev/acp/agent/goose) and documented at goose-docs.ai/docs/guides/acp-clients. Its Cargo.toml pins `agent-client-protocol = "1.0"`, `agent-client-protocol-schema = "1.1"` (unstable features), and `agent-client-protocol-http = "1.0"` (server + unstable_cancel_request features) (verified from Cargo.toml source). Separately, Goose exposes ACP over Streamable HTTP with a WebSocket upgrade via a `goose-acp` crate, intended to become the primary transport for Goose's own first-party clients (desktop Electron app, a new TypeScript TUI), per an explicit 4-phase migration plan discussed by maintainers (https://github.com/aaif-goose/goose/discussions/7309). Auth for that HTTP path uses `GOOSE_SERVER__SECRET_KEY`, checked via `X-Secret-Key` header or `?token=` (https://goose-docs.ai/docs/guides/acp-clients/).

Goose is simultaneously an ACP **client**: its "ACP Providers" feature lets Goose delegate a turn to another ACP agent ([Claude Code](./claude-code.md), [Codex CLI](./codex-cli.md), Amp, Pi) via `GOOSE_PROVIDER=claude-acp|codex-acp|amp-acp|pi-acp`, passing Goose's own configured MCP extensions through to the delegate agent as MCP servers (https://goose-docs.ai/docs/guides/acp-providers/). Session resume/fork are explicitly not yet supported on that client path.

### Integration wiring

Process model: stdio subprocess for editor integration (`goose acp`, spawned by the editor/client), or long-lived HTTP+WS server (`goose serve`) for first-party clients. Permission requests and fs/terminal RPCs are handled the standard ACP way: Goose's `crates/goose/src/acp/fs.rs` issues `ReadTextFileRequest`, `WriteTextFileRequest`, `CreateTerminalRequest`, `KillTerminalRequest`, `WaitForTerminalExitRequest`, `TerminalOutputRequest`, `ReleaseTerminalRequest` back to the ACP client via `agent_client_protocol::Client` / `ConnectionTo<Client>::send_request` (source verified). This means Goose does not do fs/terminal I/O locally when acting as an ACP agent; it always round-trips through the client, exactly matching the spec's intended client-role responsibilities. MCP server configs set under the client's `context_servers` are automatically surfaced to Goose without extra wiring (goose-docs.ai/docs/guides/acp-clients).

### Channel mapping

Goose itself does not map Slack/Telegram/WhatsApp/voice into ACP sessions; that is [Buzz](./buzz.md)'s job. Buzz (Block's open-source human+agent workspace, https://engineering.block.xyz/blog/buzz) is model- and agent-agnostic and ships harnesses for Goose, Codex, and Claude Code, treating Goose as one interchangeable backend rather than privileging it (https://explainx.ai/blog/jack-dorsey-block-buzz-ai-agents-team-chat-git-2026). Inference: Buzz likely uses its own per-agent harness layer rather than raw ACP for chat-channel fan-out; this was not independently confirmed against Buzz's source.

### Callability from trogonai today

trogonai's acp-nats-agent can plausibly spawn `goose acp` as a stdio child process the same way Zed does, bridging stdin/stdout JSON-RPC frames onto NATS subjects. Concretely: `GOOSE_PROVIDER=<provider> GOOSE_MODEL=<model> ANTHROPIC_API_KEY=... goose acp`, cwd set to the target workspace. Headless viability is good for the LLM-provider path (just an API key env var, no interactive login), but poor if using Goose's ACP-Providers-as-client mode with Claude Code/Codex, since those require their own OAuth device/login flows. The main unverified risk is ACP schema/version skew: Goose pins ACP SDK 1.0/1.1 while trogonai pins SDK 2.0.0 wire v1; the initialize/capabilities handshake needs to be checked for compatibility before treating this as a drop-in.

### Design lessons

Copy: strict separation of agent-role and client-role responsibilities, Goose never touches the filesystem or terminal directly under ACP, it always calls back through the client's fs/terminal RPCs, which is the cleanest possible boundary discipline and worth mirroring in trogonai's own ACP agent implementations. Also worth copying: exposing both a lightweight stdio transport for editor-style clients and a separate HTTP/WS transport for first-party long-lived clients, rather than forcing one transport to serve both use cases.

Avoid: Goose's ACP-Providers client mode has no session resume/fork, a known gap; trogonai should not replicate that limitation if it builds an analogous "call out to another ACP agent" capability. Also avoid conflating governance-driven repo moves (block/goose to aaif-goose/goose) with a fork; trogonai's own docs referencing Goose should track the canonical org going forward.
