# Claude Code (via the claude-code-acp / claude-agent-acp adapter)

Produced by the ACP product case-study pass (2026-07-30), then adversarially verified; corrections below override the body where they conflict.

## Claude Code, reached through the claude-code-acp / claude-agent-acp adapter

### Summary

Claude Code has no native Agent Client Protocol (ACP) support. The bridge is a separate, actively maintained TypeScript package that wraps the official Claude Agent SDK and speaks ACP on its behalf. The package has moved twice: it began as `@zed-industries/claude-code-acp`, was renamed to `@zed-industries/claude-agent-acp`, and now lives as `@agentclientprotocol/claude-agent-acp` at github.com/agentclientprotocol/claude-agent-acp, "to better allow multiple teams to contribute and maintain the adapter" (per the migration notice on the deprecated npm package, https://www.npmjs.com/package/@zed-industries/claude-code-acp). Latest published version at retrieval time is 0.63.0 (2026-07-27), Apache-2.0 licensed, `engines.node >=22`.

### What the adapter owns vs. the SDK

The adapter is thin protocol glue, not a reimplementation. It depends on `@anthropic-ai/claude-agent-sdk@0.3.220` for all agent behavior (the loop, tools, permission semantics, session transcript persistence) and on `@agentclientprotocol/sdk@1.3.0` for ACP framing; it reports `protocolVersion: 1` at initialize. What the adapter itself adds: (1) the stdio transport wiring, wrapping `process.stdin`/`process.stdout` as web streams and redirecting all console logging to stderr so nothing corrupts the JSON-RPC stream (`src/index.ts`, `runAcp()` in `src/acp-agent.ts`); (2) mapping ACP RPCs onto SDK calls, e.g. `requestPermission` -> `methods.client.session.requestPermission`, `readTextFile`/`writeTextFile` -> `methods.client.fs.*`; (3) an auth-method menu built from the SDK's own login flows; (4) an invented extension for nested subagent transcripts, since "ACP 1.2 has no standard subagent tool kind," gated behind `clientCapabilities._meta["subagent-transcript"]`; (5) MCP server config merging between ACP session params and local config before handing off to the SDK.

### Invocation and process model

Transport is stdio subprocess, full stop: an ACP client spawns `claude-agent-acp` (bin entry, `dist/index.js`) and talks JSON-RPC over its stdin/stdout. There is also a `--cli` passthrough flag that spawns the real native Claude CLI binary with inherited stdio and forwarded signals, used internally to run `claude /login`, not as a general operating mode.

### Auth

Three real paths. Non-interactive: set `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` (plus Bedrock/Vertex env switches if applicable) in the spawned process's environment; the underlying SDK subprocess picks these up directly, no ACP-level auth exchange needed. Interactive/OAuth: the adapter advertises ACP `AuthMethod` entries of type `"terminal"` (`claude-ai-login`, `console-login`) whose `args` re-invoke itself with `--cli auth login --claudeai` or `--console`; a client with terminal capability runs this and a human completes a browser or TUI flow. It also detects remote/SSH environments (`SSH_CONNECTION`, `SSH_TTY`, `NO_BROWSER`, `CLAUDE_CODE_REMOTE`) and substitutes a TUI-friendly login for the browser redirect. A fourth mode, custom-gateway auth (`gateway`, `gateway-bedrock`), is offered only when the client advertises `clientCapabilities.auth._meta.gateway`.

### Headless viability and callability from trogonai

trogonai can spawn this adapter as an ACP agent today over stdio, driving `session/new` (with MCP server passthrough), `session/prompt`, `session/load` for resume, and `session/cancel`, provided it manages a Node >=22 child process and injects `ANTHROPIC_API_KEY` for unattended auth. That is the only headless-viable auth path; the OAuth/subscription logins require a terminal RPC and a human. Before depending on capability fields, trogonai should diff its pinned ACP schema (1.5.0/1.6.0 per its conformance policy) against this adapter's `@agentclientprotocol/sdk@1.3.0` dependency, since the adapter's `providers/*` methods, `sessionCapabilities.fork/list/delete`, and `mcpCapabilities.sse` are all adapter-declared extensions layered on core ACP.

### Channel mapping and design lessons

No evidence the adapter or Claude Code map Slack/Telegram/WhatsApp/voice channels into ACP sessions; ACP here is strictly the editor/CLI-client boundary. Lessons for trogonai: (1) a thin, single-purpose stdio adapter that owns only transport and RPC mapping, leaving all agent logic to the vendor SDK, is a clean template trogonai could apply to other non-ACP-native CLIs; (2) auth-method advertisement as ACP protocol data (rather than out-of-band config) cleanly separates unattended and interactive auth, worth copying; (3) inventing `_meta` extensions for gaps in the spec (subagent transcripts) is pragmatic but creates adapter-specific coupling trogonai should track explicitly rather than assume is portable across ACP agents; (4) betting on a community/vendor-controlled npm package that migrated organizations twice in its short life is a governance risk trogonai should watch, not ignore.

### Corrections (authoritative where they conflict with the body)

Claim 2 should be corrected to: trogonai does not today contain any code that spawns the Claude ACP adapter (or any external ACP agent) as a child process and drives it as an ACP client host. The acp crates (acp-nats-agent, acp-nats-stdio, acp-nats-server) implement the opposite role: trogonai is the ACP agent/server, hosted by and driven by an external ACP client (e.g. an editor), bridged over NATS. A repo-wide search for claude-agent-acp, claude-code-acp, npx, and process-spawning calls in the acp crates returns zero hits. Building the scenario described (a Rust component spawning `npx @agentclientprotocol/claude-agent-acp`, wiring its stdio as a JSON-RPC transport, and driving it via session/new, session/prompt, session/load, session/cancel) would be new work, not an existing capability, though nothing in the adapter's own protocol surface (stdio transport, protocolVersion 1, terminal AuthMethods, env-var-based API-key auth) would block building it. Separately, the claim's framing that "providers/* ... should be diffed ... before depending on them" understates a risk that is already resolved: docs/architecture/acp-conformance.md in trogonai already marks providers/list, providers/set, and providers/disable as unrepresentable at the pinned Rust SDK 2.0.0 boundary, so that gap is known today, not merely an open question. All other sub-claims (auth env vars, terminal AuthMethod gating, gateway capability gating, adapter renaming/deprecation history, stdio transport and stderr redirection, --cli passthrough mode, remote-detection env vars, version numbers and publish dates) are confirmed against primary sources.
