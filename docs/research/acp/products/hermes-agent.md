Produced by the ACP product case-study pass (2026-07-30), then adversarially verified; corrections below override the body where they conflict.

## Hermes Agent (NousResearch/hermes-agent) - ACP case study

Hermes Agent is Nous Research's self-improving, self-hosted personal AI agent (CLI, TUI, messaging gateway, Electron app), MIT licensed, ~211k+ stars. This dossier focuses narrowly on the ACP client boundary.

### 1. ACP status

Hermes implements ACP natively, as an agent (server) exposed to editor/host clients. The implementation lives in the `acp_adapter` Python package inside the main repo, not a separate crate or fork. It depends on the official Zed-originated Python SDK `agent-client-protocol` (PyPI: https://pypi.org/project/agent-client-protocol/, docs at agentclientprotocol.github.io/python-sdk, repo github.com/agentclientprotocol/python-sdk), pinned in `pyproject.toml` as `agent-client-protocol==0.9.0` under the optional `[acp]` extra. Current PyPI latest is 0.11.1, so Hermes trails the SDK by a few minor versions; the adapter also explicitly requests `use_unstable_protocol=True` in its boot call, signalling the maintainers know they are riding a protocol still settling. Maturity reads as production-supported (documented install path, troubleshooting section, VS Code/Zed/JetBrains/Buzz integration guides) rather than experimental, though there is no explicit "stable" designation. A GitHub tracking issue for this feature (#569, opened 2026-03-07) remains open and unclosed despite the feature having shipped, which is a stale-issue-hygiene artifact, not evidence of non-implementation, confirmed by reading the live `pyproject.toml`, the `acp.md` and `acp-internals.md` docs pages, and the `[acp]` script entry `hermes-acp = "acp_adapter.entry:main"` directly from the repo.

### 2. Integration wiring

Process model: stdio subprocess. A host (editor, [Buzz](./buzz.md)'s `buzz-acp` bridge, or in principle trogonai) spawns `hermes acp` and speaks JSON-RPC over stdin/stdout; Hermes routes all human-readable logs to stderr to keep the transport clean. `HermesACPAgent` (`acp_adapter/server.py`) wraps the existing synchronous `AIAgent` core, running it in a `ThreadPoolExecutor` and bridging callbacks back to the asyncio ACP loop via `asyncio.run_coroutine_threadsafe`. Session lifecycle: `new_session(cwd)` creates a `SessionState` plus an `AIAgent(platform="acp", enabled_toolsets=["hermes-acp"])`; sessions are tracked in-memory by a thread-safe `SessionManager`; `fork_session()` deep-copies history; `cancel()` sets a cancel event and calls `agent.interrupt()`. Notably, ACP `list/load/resume/fork` are scoped only to the currently running ACP server process, even though the underlying `AIAgent` still persists to Hermes' shared `~/.hermes/state.db`. Permission requests map three ACP tiers (allow_once, allow_session, allow_always) plus deny onto Hermes' own approval semantics, with deny-by-default on timeout. MCP passthrough exists in a specific, asymmetric way: Hermes starts every globally configured MCP server from `config.yaml` before entering the ACP loop by default; a host can skip only that global startup via `HERMES_ACP_SKIP_CONFIGURED_MCP=1`, while MCP servers passed explicitly through `session/new` are always registered regardless.

### 3. Channel mapping

ACP is editor/IDE-scoped, not the mechanism for Hermes' messaging channels. Telegram, Discord, Slack, WhatsApp, and Signal are handled by a separate `gateway` platform process with its own per-platform code, entirely independent of ACP; see [channel mapping](../channel-mapping.md) for the general pattern. Hermes documents three distinct programmatic surfaces side by side (ACP, a TUI-gateway JSON-RPC protocol, and an OpenAI-compatible HTTP API), all driving the same `AIAgent` core but chosen based on transport needs, not layered on top of each other. One non-editor case does ride ACP: Buzz, a Nostr-based agent collaboration platform, ships a `buzz-acp` harness that spawns `hermes acp` as a subprocess and bridges a relay WebSocket to ACP stdio, explicitly documented as "a transport integration, not a second Hermes installation."

### 4. Callability from trogonai today

Yes, callable today via trogonai's existing `acp-nats-stdio` pattern, the same way it would spawn [Claude Code](./claude-code.md) or [Gemini CLI](./gemini-cli.md). Install `hermes-agent[acp]` (pulls `agent-client-protocol==0.9.0`), configure a model provider via `hermes model` or `~/.hermes/.env`, verify with `hermes acp --check`, then spawn `hermes acp` (or `hermes-acp`) as the ACP-side subprocess. No OAuth/device flow gates ACP itself; auth is whatever LLM provider credential Hermes already holds. Headless viability is real but risky by default: the `hermes-acp` toolset includes unrestricted `terminal` and `execute_code`, and Hermes' own docs warn that unattended hosts (Buzz Desktop) auto-approve these with `allow_once`, running shell commands with zero human check, including a documented `rm -rf` incident. Any headless trogonai integration must supply its own permission gate rather than trust Hermes' default tiers; see [secrets at spawn](../secrets-at-spawn.md) and [permission decision point](../permission-decision-point.md). MIT license imposes no constraint.

### 5. Design lessons

Copy: the three-surface split (ACP for editors, a separate JSON-RPC gateway for rich custom hosts, HTTP/SSE for OpenAI-compatible clients) cleanly matches transport to consumer instead of forcing everything through one protocol. The explicit `allow_once/allow_session/allow_always` three-tier approval model, with `allow_session` as a well-reasoned middle ground, is a stronger UX than binary allow/deny. Avoid: process-local session scoping under ACP (losing `list/load/resume` across restarts despite full persistence existing underneath) is a real gap trogonai should not replicate if it wants durable, resumable ACP sessions. Also avoid silent unattended tool-approval defaults; Hermes' own docs concede this is a live footgun rather than a solved problem.

### Corrections (authoritative where they conflict with the body)

Claim 2 should be softened: ACP is a standard stdio JSON-RPC protocol, so in principle a Rust ACP client/host could launch `hermes acp` the same way it would launch any compliant ACP agent binary; however, trogonai's current acp-nats-agent and acp-nats-stdio crates (main branch, commit 058b8bee) contain no subprocess-spawning code and currently operate as a stdio-to-NATS bridge on the agent side, not as a client host that already spawns Claude Code, Gemini CLI, or codex-acp as subprocesses. Do not present the "it already targets" framing as an established fact about trogonai's codebase.

The session-persistence sub-claim in claim 2/3 should be corrected to note a direct conflict between Hermes' own official docs: website/docs/user-guide/features/acp.md says ACP list/load/resume/fork are scoped to the currently running ACP server process (not persisted history), while website/docs/developer-guide/acp-internals.md's "Current limitations" section says ACP sessions ARE persisted to the shared ~/.hermes/state.db and transparently restored across process restarts, appearing in session_search. Treat this as an open discrepancy in Hermes' own documentation rather than a settled fact in either direction until confirmed against the acp_adapter source code itself (acp_adapter/session.py).
